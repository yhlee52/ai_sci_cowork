## 1. 이 환경은 무엇인가요

ML/DL 연구를 하는 **작은 AI 연구실**이에요. 사람은 교수님(사용자) 한 명이고, 나머지 연구원은 모두 AI입니다.

- 연구원들은 **랩미팅**에서 각자의 관점으로 토론하고, 교수님께 의견을 여쭙니다.
- 문헌 조사, 실험 구현과 실행, 비평, 보고서 작성은 담당 연구원(AI agent)이 맡아요.
- **중요한 결정은 반드시 교수님이** 내립니다. 연구원들이 멋대로 방향을 바꾸지 않아요.
- 모든 기록은 **ID가 붙은 작은 파일**로 쌓여서, 나중에 필요한 것만 골라 찾아볼 수 있어요.
- 모든 산출물(회의록, 보고서, 코드 주석, 그림 글자까지)은 **한글**로 만들어집니다.

### 연구실 사람들

| 이름 | 역할 | 이렇게 말해요 |
|---|---|---|
| **교수님** (사용자) | 방향 설정, 중요한 결정 | — |
| 윤하진 | 수석연구원, 회의 진행 | 논점을 번호로 정리하고, 교수님께 결정할 것을 여쭙니다 |
| 서도윤 | 이론·아이디어 | 새로운 가설을 과감하게 제안해요 |
| 민채원 | 문헌 조사 | "이미 된 것"과 "남은 빈틈"을 출처와 함께 말해요 |
| 강태오 | 구현·실험 | GPU 8GB 안에서 되는지, 재현되는지를 따져요 |
| 오세린 | 비평 (Reviewer 2) | 통계, 누수, 과잉 주장을 집요하게 확인해요 |
| 한유나 | 분석·작성 | 결과를 한 문장과 한 장의 그림으로 정리해요 |
| 아이디어 발상가들 | 브레인스토밍 전용 | 서로 다른 관점으로 따로따로 아이디어를 내요 |
| 기록 담당 | 사서 | 세션이 끝나면 기록을 지식베이스로 정리해요 |

### 전체 그림

```
[이 저장소: 환경]  ── 설치 ──▶  [Claude Code]
                                   │  /ai-lab:new-lab
                                   ▼
                        [연구실 폴더: 연구 결과물이 쌓이는 곳, 별도 git 저장소]
                                   │  /ai-lab:release
                                   ▼
                        [회사: Claude 없이 결과물 패키지만 사용]
```

- **이 저장소**(`initialize`)에는 환경만 들어 있어요. 연구 결과물은 여기에 쌓이지 않습니다.
- 연구는 **연구실 폴더**에서 해요. 주제마다 연구실을 따로 만들 수 있어요.
- 연구실은 **회사 밖에서만** 운영하고, 회사 안에서는 릴리스 패키지만 씁니다 (12장).

## 3. 설치하기

VSCode의 Claude Code 채팅창에 아래 두 줄을 차례로 입력하세요. **한 번만** 하면 됩니다. GitHub 저장소([yhlee52/ai_sci_cowork](https://github.com/yhlee52/ai_sci_cowork))에서 바로 받아 오기 때문에 어느 PC에서든 똑같이 하면 돼요.

```
/plugin marketplace add yhlee52/ai_sci_cowork
/plugin install ai-lab@ai-sci-cowork
```

- 첫 줄은 "이 GitHub 저장소를 plugin 목록(marketplace)으로 등록해 줘"라는 뜻이에요.
- 둘째 줄은 "그 목록에서 `ai-lab`이라는 plugin을 설치해 줘"라는 뜻이에요.

설치가 끝나면 Claude Code를 한 번 다시 시작하세요.

> 예전에 로컬 폴더 경로로 `ai-lab-local`이라는 이름으로 등록했었다면, 먼저 `/plugin marketplace remove ai-lab-local`로 지운 뒤 위 두 줄을 실행하세요.

**잘 설치됐는지 확인하기:** 채팅창에 `/ai-lab`까지 입력하면 자동 완성 목록에 `ai-lab:lab-meeting`, `ai-lab:work` 같은 명령이 보여야 해요.

## 4. 첫 연구실 만들기

### 4-1. 연구실 폴더 만들기

아무 폴더에서나 Claude Code를 열고 이렇게 입력하세요.

```
/ai-lab:new-lab D:\research\grokking-lab 작은 모델에서 grokking이 일어나는 조건
```

- 첫 번째 값은 **만들 폴더 경로**예요. 비어 있거나 아직 없는 폴더여야 합니다. 이미 뭔가 들어 있으면 아무것도 지우지 않고 멈춰요.
- 나머지는 **연구 주제**예요. 비워 두면 첫 회의에서 정합니다.
- 폴더는 자동으로 git 저장소가 돼요.

### 4-2. 연구실 폴더 열기

1. VSCode에서 **파일 → 폴더 열기**로 방금 만든 폴더를 엽니다.
2. Claude Code 패널에서 **새 세션**을 시작합니다.
3. 처음 한 번 **"이 폴더를 신뢰하시겠습니까?"** 확인이 뜨면 **승인**하세요.
   - 승인해야 연구실 설정(`.claude/settings.json`)이 적용되고, 연구원들이 지식베이스를 조회할 때마다 권한을 묻지 않아요.

세션이 시작되면 연구실 현황(장기 목표, 이번 주기, 인계 메모, 결정 대기 항목)이 자동으로 Claude에게 전달됩니다. 교수님 화면에는 보이지 않을 수 있어요. 확인하고 싶으면 `/ai-lab:lab-status`를 입력하세요.

### 4-3. 첫 회의 열기

```
/ai-lab:lab-meeting plan 연구 주제와 첫 마일스톤 정하기
```

첫 **주기 계획 회의**예요. 이 회의에서 로드맵(`ROADMAP.md`)과 이번 주기 계획(`state/cycle.md`)을 교수님과 함께 채웁니다. 자세한 흐름은 6장에서 볼게요.

## 5. 연구실 폴더 둘러보기

```
grokking-lab/
├── LAB.md              연구실 헌장: 연구 방향, 원칙, 의사결정 규칙, 데이터 규칙
├── ROADMAP.md          장기 계획: 연구 프로그램과 마일스톤
├── team.md             연구원들의 관점, 브레인스토밍 관점 목록

├── CLAUDE.md           Claude가 매번 읽는 운영 규칙 (보통 고칠 필요 없음)
├── state/
│   ├── lab_state.md    지금 상태와 인계 메모 (단기)
│   ├── cycle.md        이번 주기의 목표, 약속, 예산 (중기)
│   ├── inbox.json      교수님 결정 대기함
│   ├── actions.json    할 일 목록
│   └── counters.json   ID 번호표
├── kb/                 지식베이스 (9장)
│   ├── README.md       기록 규칙과 형식
│   ├── digest.md       연구실이 아는 것 1쪽 요약 (자동 생성)
│   ├── questions/ hypotheses/ findings/ decisions/
│   ├── papers/ datasets/ methods/ lessons/
│   └── log/            세션별 기록
├── meetings/           회의록 (session_001.md …)
├── briefs/             연구원에게 준 과업 지시서
├── research/
│   ├── ideas/          아이디어 제안서
│   ├── literature/     문헌 조사 노트
│   ├── brainstorms/    브레인스토밍 기록
│   ├── experiments/    실험 (계획, 코드, 실행 기록, 결과, 보고서)
│   ├── reviews/        비평 기록
│   ├── papers/         논문 초안
│   └── releases/       회사로 가져갈 패키지
└── labkit/             연구실 공용 실험 코드
```

**교수님이 직접 자주 볼 파일은 이 정도예요.**

| 알고 싶은 것 | 볼 파일 |
|---|---|
| 지금 어디까지 왔나 | `state/lab_state.md` 또는 `/ai-lab:lab-status` |
| 이번 주기의 목표 | `state/cycle.md` |
| 연구실이 지금까지 알아낸 것 | `kb/digest.md` |
| 지난 회의에서 무슨 얘기를 했나 | `meetings/session_NNN.md` |
| 실험 결과 | `research/experiments/EXP-NNN-*/report.md` |

## 6. 따라 하기: 첫 세션부터 첫 결과까지

"작은 모델의 grokking" 주제로 첫 주기를 돌리는 예시예요. 아래에 나오는 대화는 **이런 느낌이라는 예시**이고, 실제 내용은 매번 달라요.

### 단계 1. 주기 계획 회의

```
/ai-lab:lab-meeting plan 연구 주제와 첫 마일스톤 정하기
```

회의는 이런 식으로 진행돼요.

```
하진 (진행): 오늘 안건은 두 가지입니다. 1) 첫 연구 질문 정하기 2) 이번 주기 목표와 예산 정하기.
도윤: 가중치 감쇠가 grokking 시점을 얼마나 앞당기는지부터 보면 어떨까요?
채원: 2022년 원 논문에서 비슷한 관찰이 있었어요. 다만 모델 크기를 바꾼 비교는 적었어요.
태오: 모듈러 덧셈 과제면 8GB GPU로 한 번에 10분 안쪽이에요.

교수님께 질문
1. 첫 질문을 (A) 가중치 감쇠의 효과 (B) 모델 크기의 효과 중 무엇으로 할까요? [결정 필요]
2. 이번 주기 GPU 예산을 3시간으로 잡아도 될까요?
```

- 회의는 라운드마다 **멈추고 교수님의 답을 기다려요.** 그냥 대화하듯 답하면 됩니다.
  - 예: "A로 가자. 대신 모델 크기도 두 가지는 같이 봐줘. 예산은 좋아."
- 새 아이디어를 던져도 되고, 방향을 바꿔도 되고, "진행"이라고만 해도 돼요.
- 연구원이 교수님 의견에 근거를 들어 반대할 수도 있어요. 최종 결정은 교수님이 합니다.
- 회의가 끝나면 이런 것들이 자동으로 만들어져요.
  - 회의록 `meetings/session_001.md`
  - 로드맵 `ROADMAP.md`와 주기 계획 `state/cycle.md`
  - 할 일(`A-001` …)과 아이디어 제안서(`IDEA-001`)

### 단계 2. (선택) 브레인스토밍

아이디어를 더 넓게 모으고 싶을 때 써요.

```
/ai-lab:brainstorm 가중치 감쇠 외에 grokking을 앞당길 수 있는 요인
```

1. 서로 다른 관점의 발상가 여러 명이 **따로따로** 아이디어를 냅니다 (서로의 답을 보지 않아요).
2. 비슷한 아이디어를 합치고, 오세린이 새로움, 실현 가능성, 검증 가능성, 목표 적합성으로 점수를 매겨요.
3. 상위 후보를 다듬어서 **표로 올리고 교수님의 선택을 기다립니다.**
   - 예: "2번이랑 3번을 합쳐서 진행해. 1번은 보류."
4. 고른 아이디어는 제안서와 할 일(보통 문헌 확인, 파일럿)로 바뀌어요.

### 단계 3. 작업 실행

```
/ai-lab:work
```

남은 할 일을 담당 연구원들이 처리해요.

- 민채원이 선행연구를 찾아 `research/literature/LIT-001-*.md`를 씁니다.
- 강태오가 실험 계획서(`plan.md`)를 쓰고 **파일럿**(2분 이내, 시드 1개)을 돌려요. 파일럿은 교수님 승인 없이 합니다.
- 파일럿이 끝나면 이렇게 여쭤봐요.

```
EXP-001 파일럿 결과: 코드 정상 동작, 기준선 대비 신호 있음 (파일럿 수치라 증거는 아닙니다).
본 실험 계획: 조건 4개 × 시드 3개, 예상 GPU 40분.
예측: 감쇠가 클수록 일반화 시점이 30% 이상 빨라진다 / 중단 기준: 차이가 시드 간 편차보다 작으면 중단.
본 실험을 승인하시겠어요? (승인 / 축소 후 승인 / 보류)
```

- **"승인"** 이라고 하면 본 실험이 시작돼요. 이 약속(예측, 성공 기준, 중단 기준)을 미리 적어 두는 것을 **사전 등록**이라고 해요. 결과를 본 뒤에 가설을 바꾸지 못하게 막아 줍니다.
- 본 실험이 끝나면 자동으로 이어서 진행돼요.
  1. `lab.py verify`로 결과 숫자가 실제 실행 기록과 일치하는지 검사
  2. 한유나가 보고서와 그림 작성
  3. 오세린이 코드와 로그까지 확인하며 비평

### 단계 4. 결과 리뷰 회의

```
/ai-lab:lab-meeting review
```

- 보고서의 한 문장 결론, 오세린의 판정, 검증 결과를 놓고 토론해요.
- 결과마다 교수님이 정합니다. **"확정해도 돼"**, **"추가 실험 필요"**, **"기각"** 중 하나로 답하시면 돼요.
- 확정한 결과만 지식베이스에 `확정`으로 기록돼요.

### 단계 5. 세션 마무리

```
/ai-lab:archive
```

- 기록 담당이 회의록과 산출물을 지식베이스로 정리합니다. 가설 상태 변경, 새 결과, 결정, 교훈 등이 기록돼요.
- 지식 요약본(`kb/digest.md`)과 다음 세션을 위한 인계 메모가 갱신돼요.
- 이 세션이 닫히고, 다음 회의부터는 새 세션 번호가 붙어요.

### 단계 6. 주기 회고 (세션 3개마다)

```
/ai-lab:lab-meeting retro
```

- 이번 주기가 성공 기준을 달성했는지 평가해요.
- 교훈을 남기고, 로드맵을 어떻게 고칠지 제안합니다. 로드맵은 교수님이 승인할 때만 바뀌어요.
- 그다음에는 다시 `plan` 회의로 새 주기를 시작합니다.

> **한 세션을 꼭 한 번에 끝낼 필요는 없어요.** 모든 상태가 파일에 남기 때문에, 중간에 Claude Code를 닫아도 다음에 열면 인계 메모부터 이어집니다.

## 7. 명령어 사전

모든 명령은 `/ai-lab:`으로 시작해요. 다른 plugin과 이름이 겹치지 않으면 `/lab-meeting`처럼 짧게 써도 됩니다.

### `/ai-lab:lab-meeting [유형] [안건]` — 랩미팅

| 유형 | 언제 | 무엇이 남나 |
|---|---|---|
| `plan` | 주기를 시작할 때 | 이번 주기 계획(`state/cycle.md`), 필요하면 로드맵 변경 |
| `progress` | 세션 시작에 짧게 점검할 때 | 우선순위 조정, 막힌 점 |
| `review` | 실험 결과가 나왔을 때 | 결과마다 확정, 추가 실험, 기각 결정 |
| `journal <P-/LIT id>` | 논문 한두 편을 같이 읽을 때 | 요점, 아이디어 후보 |
| `retro` | 주기가 끝났을 때 | 주기 평가, 교훈, 로드맵 변경 제안 |
| `1on1 <이름>` | 한 연구원과만 얘기하고 싶을 때 | 그 연구원과의 메모, 할 일 |
| (생략) | 그 밖의 모든 논의 | 결정, 할 일 |

- 예: `/ai-lab:lab-meeting 1on1 강태오 실험 코드 구조 논의`
- 회의가 시작되면 **결정 대기함의 질문을 가장 먼저** 여쭤봐요.
- 회의록에는 교수님 발언, 결정(등급 표시), 반대 의견까지 남습니다.

### `/ai-lab:brainstorm <주제> [관점들]` — 브레인스토밍

- 관점은 `team.md`에 있어요: `theory`(이론), `empirical`(실험 우선), `contrarian`(반대 의견), `literature-gap`(선행연구의 빈틈), `cross-domain`(다른 분야의 유추), `simplify`(단순화).
- 관점을 직접 고를 수도 있어요: `/ai-lab:brainstorm 학습률 스케줄 contrarian,simplify`
- 참여 인원은 예산 프로필에 따라 정해져요 (기본 3명).

### `/ai-lab:work [할 일 ID들]` — 작업 실행

- 비워 두면 교수님 몫을 뺀 모든 남은 할 일을 처리해요. `/ai-lab:work A-003 A-004`처럼 골라서 시킬 수도 있어요.
- 중간에 교수님 결정이 필요하면 **멈추고 여쭤봐요.** "나중에"라고 하시면 결정 대기함에 올리고, 그 결정과 상관없는 일만 계속합니다.

### `/ai-lab:archive [세션 번호]` — 세션 마무리

- 세션을 지식베이스로 정리하고 닫아요. **교수님만** 실행할 수 있는 명령이에요 (Claude가 알아서 실행하지 않아요).

### `/ai-lab:release <ID들> [목적]` — 회사용 패키지 만들기

- 12장을 보세요. 교수님만 실행할 수 있어요.

### `/ai-lab:lab-status` — 현황 보기

- 장기 목표, 주기 진행도, 결정 대기 항목, 진행 중인 일, 다음에 할 명령을 10줄 안에 알려 줘요. 가장 가볍게 현황을 보는 방법이에요.

### `/ai-lab:new-lab <경로> [주제]` — 새 연구실 만들기

- 4장을 보세요.

### 명령 없이 그냥 말해도 돼요

연구실 폴더에서는 평소처럼 말로 부탁해도 됩니다.

## 8. 교수님이 결정하는 순간들

연구가 엉뚱한 방향으로 흘러가지 않도록, 결정의 무게에 따라 누가 정하는지가 나뉘어 있어요 (`LAB.md`).

| 등급 | 예 | 누가 정하나 |
|---|---|---|
| **A. 자율** | 구현 방식, 디버깅, 승인된 계획 안의 하이퍼파라미터, 파일럿, 문헌 검색 | 담당 연구원이 알아서 |
| **B. 동료 협의** | 승인된 계획 안에서의 설계 변경, 애매한 결과의 해석 | 담당 연구원 + 다른 연구원 (주로 오세린) |
| **C. 교수님 결정** | 새 연구 방향, 본 실험 착수, 가설 폐기, 결과 확정, 예산 초과, 로드맵과 주기 목표 변경, 기존 결과와 모순될 때, 지시가 애매할 때 | **교수님** |

- 판단이 애매하면 연구원들은 한 단계 위 등급으로 취급해요.
- 모든 B, C 결정은 이유와 반대 의견과 함께 기록됩니다 (`kb/decisions/`).

### 결정 대기함 (`ASK-`)

교수님이 자리에 없거나 "나중에 정할게"라고 하면 질문이 **결정 대기함**에 올라가요.

- 다음 세션을 시작하면 Claude가 가장 먼저 알려 드려요. `/ai-lab:lab-status`에서도 맨 위에 보여요.
- 답하는 방법은 그냥 말하면 돼요: **"ASK-001은 축소 후 승인으로 할게"**.
- 쌓인 질문 목록만 보고 싶으면 "결정 대기함 보여줘"라고 하세요.

## 9. 지식 찾아보기

### 지식베이스의 구성

| 종류 | ID | 예 |
|---|---|---|
| 연구 질문 | `Q-` | "작은 모델에서 일반화 지연은 왜 생기나?" |
| 가설 | `H-` | "가중치 감쇠가 클수록 grokking이 빨라진다" |
| 결과 | `F-` | "감쇠 1e-2에서 일반화 시점이 38% 빨라짐 (확신도 중간)" |
| 결정 | `D-` | "첫 주기는 모듈러 덧셈 과제만 다룬다" |
| 논문 | `P-` | 원제 + 한 줄 요점 |
| 데이터셋 / 방법 | `DS-` / `M-` | 재사용 가능한 로더, 모델, 검증된 하이퍼파라미터 |
| 교훈 | `L-` | "Windows에서는 DataLoader의 num_workers를 0으로 둔다" |
| 세션 기록 | `S-` | 세션마다 무엇이 바뀌었는지 |

그 밖에 아이디어(`IDEA-`), 문헌 조사(`LIT-`), 실험(`EXP-`), 리뷰(`REV-`), 브레인스토밍(`BS-`), 과업(`TASK-`), 릴리스(`REL-`)에도 ID가 붙어요.

### 원칙 몇 가지

- **사실 하나는 파일 하나에만 적혀요.** 다른 곳에서는 ID로만 가리킵니다.
- 각 항목에는 **현재 상태**만 있고, **언제 왜 바뀌었는지**는 세션 기록에 남아요.
- 결과(`F-`)는 교수님이 확정해야만 `확정` 상태가 돼요. 그 전에는 `잠정`이에요.

### 찾는 방법

**가장 쉬운 방법은 Claude에게 물어보는 거예요.** "grokking 관련해서 우리가 확정한 결과 뭐 있어?"라고 하면 필요한 것만 찾아 읽고 답해요.

직접 찾고 싶으면 연구실 폴더의 터미널에서 이렇게 실행하세요 (`<환경>`은 이 저장소를 내려받은 폴더 경로예요. 모르겠으면 연구실 세션에서 "lab.py 경로 알려줘"라고 물어보세요. Claude는 세션 시작 때 정확한 경로를 전달받아요).

```
python "<환경>\scripts\lab.py" find grokking                 # 키워드로 찾기 (한 줄씩)
python "<환경>\scripts\lab.py" find --type 가설 --status "검증 중"
python "<환경>\scripts\lab.py" show H-001                      # 항목 하나 보기
python "<환경>\scripts\lab.py" context EXP-001                 # 연결된 항목까지 한 줄씩
python "<환경>\scripts\lab.py" history H-001                   # 세션별 변화 이력
python "<환경>\scripts\lab.py" digest                          # 지식 요약본 다시 만들기
```

출력 예시:

```
H-001 [가설/검증 중] 가중치 감쇠가 grokking 시점을 앞당긴다 — 감쇠가 클수록 일반화 시점이 빨라진다 #grokking  (kb/hypotheses/H-001.json)
```

`--type`에는 한글(`가설`, `결과`, `논문` …)과 영어(`hypothesis`, `finding`, `paper` …)를 모두 쓸 수 있어요. `--status`도 마찬가지예요 (`검증 중` 또는 `testing`).

> 파일 안의 상태 값과 필드 이름은 기계가 읽는 표기라서 영어로 저장돼요. 화면에 보여 줄 때만 한글로 바꿔 줍니다. 그 밖의 모든 문장(제목, 요약, 설명)은 한글이에요.

## 10. 주기와 로드맵 운영하기

### 컨텍스트의 층

연구실은 정보를 변하는 속도에 따라 나눠서 관리해요. 그래서 연구원들이 "왜 이 일을 하는지"를 잃지 않으면서도 매번 모든 기록을 읽지 않아도 됩니다.

| 층 | 파일 | 바뀌는 때 |
|---|---|---|
| 헌장 | `LAB.md` | 거의 바뀌지 않아요 |
| 장기 | `ROADMAP.md` | 주기 계획과 회고 때 (교수님 승인 필요) |
| 중기 | `state/cycle.md` | 주기 계획 때 쓰고, 세션마다 진행을 한 줄씩 추가 |
| 단기 | `state/lab_state.md` | 단계가 끝날 때마다 새로 써요 (인계 메모 포함) |
| 지식 | `kb/digest.md` → 개별 항목 | archive 때마다 |

### 목적의 사슬

모든 실험과 과업에는 이런 사슬이 적혀요.

```
MS-1 (마일스톤) → Q-001 (질문) → H-002 (가설) → EXP-003 (실험) → TASK-007 (과업)
```

그래서 실험을 맡은 연구원도 "이 실험이 어떤 마일스톤을 위한 것인지"를 알고 절충할 수 있어요.

### 주기

- 기본값은 **세션 3개가 한 주기**예요 (`lab.config.json`의 `cycle_sessions`).
- 세션 수가 차면 현황에 "회고할 때입니다"가 표시돼요.
- 흐름: `plan` 회의 → (세션마다 progress, brainstorm, work, review, archive) → `retro` 회의

## 11. 실험이 돌아가는 방식

### 단계

```
아이디어 → 파일럿 → 사전 등록 승인 → 본 실험 → 검증 → 보고서 → 비평 → 결과 확정
 (회의)    (자율)    (교수님)          (자율)   (자동)   (한유나)  (오세린)  (교수님)
```

- **파일럿**: 2분 이내, 시드 1개. 코드가 도는지, 신호가 있는지, 본 실험에 시간이 얼마나 걸릴지를 봅니다. 파일럿 수치는 **증거로 쓰지 않아요.**
- **본 실험**: 조건마다 시드 3개 이상. 한 명령은 10분을 넘지 않게 나눠 돌리고, 체크포인트에서 이어서 학습해요.
- **검증** (`lab.py verify`): `results.json`의 모든 숫자가 실제 실행 기록과 일치하는지, 사전 등록 항목이 있는지 기계적으로 검사해요.

### 실험 폴더

```
research/experiments/EXP-001-weight-decay/
├── plan.md        실험 계획 (목적의 사슬, 설정, 베이스라인, 예측, 성공 기준, 중단 기준, 예산)
├── src/           코드 (주석과 메시지는 한글)
├── configs/       조건별 설정
├── runs/          실행별 기록 (git에는 올라가지 않음)
├── results.json   결과 (코드가 자동으로 만듦)
├── report.md      한유나의 보고서
└── figures/       그림 (제목, 축, 범례 한글)
```

### 정직성 규칙

- 실행이 실패하면 **실패로 보고해요.** 가짜 데이터나 임시 값으로 메우지 않습니다.
- 너무 좋은 결과는 버그부터 의심해요 (데이터 누수 확인).
- 검증하지 않은 조건으로 결론을 넓히지 않아요. 보고서에는 "검증하지 않은 범위"가 따로 적혀요.

### GPU와 Python 환경

- 첫 실험 때 강태오가 `uv sync`와 `uv add torch torchvision`으로 연구실 폴더 안에 환경을 만들어요 (CUDA 12.8용 torch, Python 3.11~3.13).
- 실험 실행(`uv run`)은 기본적으로 **매번 승인을 물어요.** 번거로우면 13장을 보세요.

## 12. 회사로 결과물 가져가기

### 데이터 규칙 (가장 중요)

연구실에서 읽는 모든 내용은 Claude API로 전송돼요. 그래서 이 규칙은 꼭 지켜 주세요.

- **회사 데이터, 사내 코드와 문서, 사내 수치, 고객 정보는 연구실에 넣지 않아요.**
- 공개 데이터, 공개 논문, 직접 만든 합성 데이터만 씁니다.
- 회사 문제를 다루고 싶으면 **기밀이 아닌 일반화된 형태로** 설명해 주세요.
  - 예: "사내 설비 센서 데이터" → "다변량 시계열 이상 탐지, 샘플 1만 개, 변수 20개 규모"

### 릴리스 만들기

```
/ai-lab:release F-003 EXP-005 설비 이상 탐지 기준선으로 사용
```

1. 무엇을 넣을지 목록을 보여 드리고 **승인을 기다려요.**
   - 포함할 것과 뺄 것
   - 확정되지 않은 결과가 섞여 있는지 (넣으면 "미확정"으로 표시)
   - 데이터셋, 모델, 코드의 **회사 사용 가능 라이선스** 여부
2. 승인하면 `research/releases/REL-001-*/`에 패키지를 만들어요.
   - `README.md`: 무엇을 주는지, 근거, 적용 범위와 한계, 오프라인 설치법, 재현 정보, 라이선스
   - `code/`: 필요한 코드만 (공용 코드도 복사해서 **단독으로 실행**됨)
   - `configs/`, `results/`, `requirements.txt`(버전 고정), `MANIFEST.txt`(파일 무결성 목록)
3. 새 가상환경에 설치해서 실제로 돌아가는지 확인한 뒤 zip으로 묶어요.

### 회사 안에서 설치하기 (인터넷 없는 PC)

README에도 적혀 있지만 요약하면 이래요.

1. 인터넷이 되는 PC에서: `pip download -r requirements.txt -d wheels/`
2. zip과 `wheels/` 폴더를 승인된 방법으로 반입
3. 회사 PC에서: `pip install --no-index --find-links wheels/ -r requirements.txt`
4. README의 "사용법"대로 실행

패키지에는 지식베이스, 회의록, API 키, 개인 경로가 **절대 들어가지 않아요.**

## 13. 설정 바꾸기

### 예산 프로필 (`lab.config.json`)

`budget_profile` 값을 바꾸면 연구실 전체의 "성실함"이 함께 바뀌어요.

| 항목 | `economy` (기본) | `standard` | `deep` |
|---|---|---|---|
| 회의 라운드 | 2 | 3 | 4 |
| 라운드당 발언자 | 3 | 4 | 6 |
| 리뷰 횟수 | 1 | 1 | 2 (비평가 두 명이 따로) |
| 동시에 일하는 연구원 | 1 | 2 | 3 |
| 문헌 수 | 5 | 8 | 15 |
| 브레인스토밍 인원 | 3 | 4 | 6 |

주기 길이는 `cycle_sessions`, 한 번 실행의 최대 시간은 `compute.max_run_minutes`로 바꿔요.

### 연구원 관점 바꾸기 (`team.md`)

표의 "관점 / 발언 경향"을 고치면 회의에서의 성격이 바뀌어요. 브레인스토밍 관점도 여기서 추가하거나 순서를 바꿀 수 있어요 (위에서부터 쓰여요).

### 모델 바꾸기

- 메인 대화(회의 진행)는 Claude Code에서 `/model`로 바꿔요. 일상 운영에는 `sonnet`을 권해요.
- 실무 연구원들은 기본으로 sonnet을 써요. 바꾸려면 이 저장소의 `agents/<이름>.md` 맨 위 `model:` 값을 고치세요 (15장).

### 실험 실행 권한

실험 명령을 매번 승인하기 번거로우면 연구실 폴더의 `.claude/settings.json`을 이렇게 고치세요.

```json
{
  "permissions": {
    "allow": [
      "Bash(python *lab.py*)",
      "Bash(uv run *)"
    ]
  }
}
```

`uv run`을 허용하면 연구원이 파이썬 코드를 묻지 않고 실행할 수 있게 된다는 점만 기억하세요.

## 14. 문제 해결 (FAQ)

**Q. 세션을 열었는데 연구원들이 연구실 상황을 모르는 것 같아요.**
- 연구실 **폴더 자체**를 열었는지 확인하세요 (상위 폴더가 아니라). `lab.config.json`이 있는 폴더예요.
- plugin이 설치되어 있는지 `/ai-lab`을 입력해서 확인하세요.
- `/ai-lab:lab-status`를 실행하면 현황을 다시 읽어요.

**Q. 연구원들이 지식을 찾을 때마다 권한을 물어봐요.**
- 연구실 폴더를 처음 열 때 신뢰(trust) 확인을 승인하지 않았을 수 있어요. VSCode를 다시 열고 새 세션에서 승인하세요.

**Q. 그림의 한글이 네모로 깨져요.**
- 그림을 그리기 전에 `labkit.setup_korean_plot()`을 불러야 해요 (연구원들에게는 이미 규칙으로 들어 있어요).
- 한글 글꼴이 없으면 경고가 나와요. Windows는 맑은 고딕이 기본으로 있어요.

**Q. 터미널에 한글이 깨져서 나와요.**
- `lab.py`와 `labkit`은 UTF-8로 출력하도록 되어 있어요. 직접 짠 스크립트라면 맨 위에 `import labkit`을 넣거나, 환경 변수 `PYTHONUTF8=1`을 설정하세요.

**Q. torch 설치가 안 돼요 / GPU를 못 잡아요.**
- `nvidia-smi`로 드라이버를 확인하세요. `pyproject.toml`은 CUDA 12.8용 torch를 받도록 되어 있어요. 드라이버가 오래됐다면 `pyproject.toml`의 `cu128`을 맞는 버전으로 바꾸세요.
- Python은 3.11~3.13을 써요 (uv가 알아서 받아요).

**Q. 사용 한도에 걸려서 중간에 멈췄어요.**
- 걱정하지 않으셔도 돼요. 상태가 모두 파일에 있어요. 한도가 풀린 뒤 새 세션을 열면 인계 메모부터 이어집니다.
- 긴 대화는 단계 사이마다 `/clear`로 비우면 사용량이 크게 줄어요. 상태는 세션 시작 hook이 다시 불러와요.

**Q. 기록이 잘못됐어요 (예: 결과가 잘못 확정됨).**
- 파일을 직접 지우지 말고 Claude에게 말하세요: "F-004는 잘못 확정됐어. 대체됨으로 바꾸고 이유를 남겨줘." 이력이 남는 방식으로 고쳐 줘요.
- 급하면 해당 JSON 파일을 직접 고친 뒤 `lab.py index`와 `lab.py digest`를 실행하세요.

**Q. 결정 대기함에 오래된 질문이 쌓였어요.**
- "결정 대기함 정리하자"라고 하면 하나씩 여쭤보고 정리해요.

**Q. 연구실을 하나 더 만들고 싶어요.**
- `/ai-lab:new-lab`으로 다른 폴더에 만들면 돼요. 연구실끼리는 기록이 섞이지 않아요.

## 15. 환경 자체를 고치고 싶을 때

이 저장소(`initialize`)를 고치면 모든 연구실의 동작이 바뀌어요.

| 바꾸고 싶은 것 | 고칠 파일 |
|---|---|
| 연구원의 일하는 방식, 모델 | `agents/<이름>.md` (`model:`, `effort:` 등) |
| 명령의 흐름 | `skills/<명령>/SKILL.md` |
| 세션 시작 시 불러오는 내용 | `scripts/lab.py`의 `status`, `hooks/hooks.json` |
| **새로 만드는** 연구실의 기본 파일 | `templates/workspace/` |

- `templates/workspace/`를 고쳐도 **이미 만든 연구실에는 적용되지 않아요.** 기존 연구실은 해당 파일을 직접 고치세요.
- 고친 뒤에는 `.claude-plugin/plugin.json`의 `version`을 올리고 GitHub에 올린(push) 다음, Claude Code에서 아래를 실행하고 다시 시작하세요. 한 단계씩 설명은 [처음 읽는 안내서](처음_읽는_안내서.md)의 "GitHub으로 관리하기"에 있어요.

```
/plugin marketplace update ai-sci-cowork
```

- 설치 없이 바로 시험해 보려면 CLI에서 `claude --plugin-dir "<이 저장소 경로>"`로 실행할 수 있어요.

## 16. 용어 정리

| 용어 | 뜻 |
|---|---|
| 세션 | 한 번의 작업 묶음. 회의부터 archive까지. 번호가 붙어요 (001, 002 …) |
| 주기 | 세션 몇 개의 묶음 (기본 3). 계획 회의로 시작해 회고로 끝나요 |
| 마일스톤 (MS) | 로드맵의 중간 목표 |
| 파일럿 | 2분 이내의 작은 시험 실행. 증거로 쓰지 않아요 |
| 사전 등록 | 본 실험 전에 예측, 성공 기준, 중단 기준을 미리 적는 것 |
| 본 실험 | 교수님이 승인한 계획대로, 시드 3개 이상으로 돌리는 실험 |
| 결정 등급 (A/B/C) | 자율 / 동료 협의 / 교수님 결정 |
| 결정 대기함 (ASK) | 교수님 답을 기다리는 질문 목록 |
| 지식베이스 (kb) | ID가 붙은 연구 지식 파일 모음 |
| 지식 요약본 (digest) | 연구실이 아는 것을 1쪽으로 정리한 자동 생성 문서 |
| 인계 메모 | 다음 세션이 가장 먼저 읽는, 하던 일과 다음 할 일 |
| 과업 지시서 (brief) | 연구원에게 일을 맡길 때 주는 40줄 이하의 지시서 |
| 목적의 사슬 | 마일스톤 → 질문 → 가설 → 실험 → 과업으로 이어지는 연결 |
| 릴리스 (REL) | 회사에서 Claude 없이 쓸 수 있게 만든 독립 실행 패키지 |
| labkit | 연구실 공용 실험 코드 (실행 기록, 결과 집계, 학습 루프, 한글 그림) |
| `lab.py` | ID 발급, 검색, 검증, 요약본 생성을 하는 도구 |
