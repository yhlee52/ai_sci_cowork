## 1. AI agent란 무엇인가요

### 챗봇과 agent의 차이

| | 챗봇 | agent |
|---|---|---|
| 하는 일 | 질문에 **대답**한다 | 목표를 받아 **일을 해낸다** |
| 쓸 수 있는 것 | 말(텍스트)만 | 도구: 파일 읽고 쓰기, 터미널 명령 실행, 웹 검색 등 |
| 예 | "grokking이 뭐야?" → 설명 | "grokking 실험을 짜서 돌려 줘" → 코드를 쓰고, 실행하고, 오류를 고치고, 결과를 정리 |

agent는 이런 **순환**을 반복하면서 일해요.

```
① 생각한다: "먼저 데이터 로더가 있는지 확인해야겠다"
② 도구를 쓴다: 폴더 목록 보기
③ 결과를 본다: "labkit에 이미 있네"
④ 다음 행동을 정한다 → 다시 ①로
   … 목표를 이룰 때까지 반복
```

### Claude Code

지금 쓰고 계신 **Claude Code**가 바로 agent예요. Claude(AI 모델)에게 아래 것들을 붙여 놓은 프로그램입니다.

- **도구**: 파일 읽기/쓰기/고치기, 터미널 명령 실행, 웹 검색, 다른 agent 부르기 등
- **권한 시스템**: 위험할 수 있는 행동(명령 실행 등) 전에 사용자에게 허락을 구해요.
- **확장 기능**: 규칙 파일, 절차서(skill), 자동 실행(hook), 보조 agent(subagent) 등을 붙일 수 있어요.

> **비유:** 아주 똑똑하고 성실하지만, **매일 아침 어제 일을 전혀 기억하지 못하는** 신입 연구원에게 연구실 컴퓨터를 빌려준 것과 비슷해요. 그래서 이 연구원이 매일 제대로 일하려면 "연구 노트"가 아주 중요해집니다. 이 환경의 대부분은 바로 그 연구 노트를 잘 쓰고 잘 읽게 만드는 장치예요.

## 2. 꼭 알아야 할 개념들

### 2-1. 컨텍스트와 토큰 — AI의 "작업 기억"

- **컨텍스트**는 AI가 한 번에 머릿속에 올려 둘 수 있는 내용이에요. 지금까지의 대화, 읽은 파일, 도구 결과가 모두 여기에 들어가요.
- **토큰**은 그 내용을 재는 단위예요 (대략 한글 한두 글자, 영어 단어 한 조각 정도).
- 중요한 점 두 가지:
  1. **크기에 한계가 있어요.** 너무 많이 읽으면 오래된 내용은 요약되거나 밀려나요.
  2. **읽는 양만큼 비용(사용량)이 들어요.** 대화가 길어질수록 매 요청마다 그 전체를 다시 보내요.

> 그래서 이 연구실은 "모든 걸 다 읽지 말고, **ID로 필요한 것만 찾아 읽는다**"를 가장 중요한 원칙으로 삼아요.

### 2-2. 세션 — 대화 하나

- Claude Code에서 새 대화를 시작하면 **새 세션**이에요.
- 세션이 끝나면 AI는 그 내용을 **기억하지 못해요.** (1장의 "매일 아침 기억을 잃는 신입 연구원")
- 그래서 이 연구실은 세션이 끝날 때마다 **인계 메모**(`state/lab_state.md`)를 남기고, 다음 세션이 시작될 때 자동으로 읽게 해요.
- `/clear`는 지금 대화를 비우고 새로 시작하는 명령이에요. 파일에 남은 기록은 그대로 있어요.

### 2-3. CLAUDE.md — 매번 읽는 규칙집

- 폴더에 `CLAUDE.md`라는 파일이 있으면, Claude는 **그 폴더에서 일할 때마다 자동으로** 읽어요.
- 비유: 연구실 문 앞에 붙어 있는 **"연구실 규정"**.
- 우리 연구실 폴더의 `CLAUDE.md`에는 "모든 산출물은 한글", "중요한 결정은 교수님께", "회사 데이터는 넣지 않는다" 같은 규칙이 들어 있어요.
- 매번 읽히기 때문에 **짧게** 유지해요. 긴 설명은 다른 파일에 두고 필요할 때만 읽게 합니다.

### 2-4. Subagent — 보조 연구원

- 메인 Claude가 일을 **다른 AI에게 맡기는** 기능이에요. 맡겨진 AI를 subagent라고 불러요.
- subagent는 **자기만의 깨끗한 컨텍스트**에서 일하고, 끝나면 **짧은 보고서만** 돌려줘요.
- 장점:
  - 메인 대화가 실험 로그 같은 긴 내용으로 가득 차지 않아요.
  - 역할마다 성격, 규칙, 도구, 모델을 다르게 줄 수 있어요 (비평가는 꼼꼼하게, 문헌 조사원은 웹 검색 가능하게).
  - 여러 명이 **동시에** 일할 수 있어요.
- 단점: 각자 따로 요청을 보내므로 **사용량이 늘어요.** 그리고 대화 내용을 모르고 시작하기 때문에, 맡길 때 **지시서**(우리 연구실의 `briefs/TASK-*.md`)를 잘 써 줘야 해요.
- 파일 위치: `agents/<이름>.md` (예: `agents/engineer.md` = 강태오)

### 2-5. Skill — 절차서

- **정해진 일의 순서를 적어 둔 문서**예요. `/이름`으로 불러내면 Claude가 그 절차대로 일해요.
- 비유: 연구실의 **표준 작업 절차서(SOP)**. "랩미팅은 이렇게 진행한다", "세션을 마칠 때는 이렇게 정리한다".
- 우리 연구실의 `/ai-lab:lab-meeting`, `/ai-lab:work` 같은 명령이 모두 skill이에요.
- 파일 위치: `skills/<이름>/SKILL.md`

### 2-6. Hook — 자동 실행 장치

- **특정 순간에 자동으로 실행되는 스크립트**예요. AI가 판단해서 하는 게 아니라, 프로그램이 무조건 실행해요.
- 우리 연구실에는 hook이 하나 있어요: **세션이 시작될 때** 연구실 현황(장기 목표, 이번 주기, 인계 메모, 결정 대기 항목)을 자동으로 Claude에게 알려 줘요.
- 비유: 연구실에 들어오면 **자동으로 켜지는 칠판**. 누가 켜라고 하지 않아도 켜져요.
- 파일 위치: `hooks/hooks.json`

### 2-7. Plugin과 marketplace — 설치 꾸러미

- **Plugin**은 agent, skill, hook을 한데 묶어 **설치할 수 있게 만든 꾸러미**예요. 이 저장소 전체가 `ai-lab`이라는 plugin 하나예요.
- **Marketplace**는 plugin 목록이에요. 우리 저장소가 곧 marketplace(`ai-sci-cowork`)이기도 해서, GitHub 주소만 등록하면 설치할 수 있어요.
- plugin의 명령은 이름 앞에 plugin 이름이 붙어요: `/ai-lab:lab-meeting`.

### 2-8. 권한과 신뢰(trust)

- Claude가 파일을 고치거나 명령을 실행하기 전에 **허락을 구하는 창**이 뜰 수 있어요. 무엇을 하려는지 읽고 승인하거나 거절하면 돼요.
- 폴더를 처음 열면 **"이 폴더를 신뢰하시겠습니까?"** 확인이 떠요. 승인해야 그 폴더의 설정(`.claude/settings.json`)이 적용돼요. 우리 연구실은 이 설정에서 "지식 검색 도구(`lab.py`)는 묻지 말고 실행"을 허용해 둬요.

### 2-9. Agent 기억 (memory)

- 일부 연구원(subagent)은 **연구실별로 자기 기억**을 쌓을 수 있어요. 예를 들어 강태오는 "이 PC에서는 DataLoader의 num_workers를 0으로 해야 한다" 같은 노하우를 기억해요.
- 세션을 넘어서도 남는, 그 연구원만의 수첩이라고 생각하면 돼요.

### 2-10. 목표 모드 (`/goal`) — 자리를 비운 동안 이어서 일하게 하기

- 보통 Claude는 한 번 답하고 나면 교수님의 다음 말을 기다려요. `/goal 조건`을 쓰면, **조건이 충족될 때까지 스스로 다음 턴을 이어 가요.** 매 턴이 끝날 때마다 작은 모델이 "조건이 충족됐나?"를 확인해요.
- 사용 한도에 걸리면 한도가 풀린 뒤 자동으로 이어 가요. 그래서 **자율 탐색 캠페인**을 자리를 비운 사이나 밤새 오래 맡길 때 써요 ([사용설명서 12장](사용설명서.md#12-자율-탐색-캠페인)). 지켜보면서 바로 돌릴 때는 필요 없어요.
- 비유: 퇴근하면서 "이 목록 다 끝날 때까지 계속해 줘"라고 적어 둔 메모.

## 3. 우리 연구실은 이 개념들로 어떻게 만들어졌나요

| 실제 연구실 | 이 환경에서 | 무엇으로 만들었나 |
|---|---|---|
| 지도교수 | **교수님** (사용자 본인) | — |
| 연구실 규정 | `LAB.md` (원칙, 의사결정 규칙, 데이터 규칙) + `CLAUDE.md` | 규칙 파일 |
| 랩미팅 | `/ai-lab:lab-meeting` | skill (메인 Claude가 여러 연구원의 관점으로 발언) |
| 연구원들 | 민채원, 강태오, 오세린, 한유나, 기록 담당, 아이디어 발상가들 | subagent |
| 일 맡기기 | `/ai-lab:work` + 과업 지시서(`briefs/`) | skill + 파일 |
| 브레인스토밍 | `/ai-lab:brainstorm` | skill + 여러 subagent를 동시에 |
| 출근하면 보는 칠판 | 세션 시작 시 현황 자동 전달 | hook |
| 연구 노트, 실험 노트 | `meetings/`, `research/`, `kb/` | 파일 |
| 연구실 공용 코드 | `labkit/` | 파이썬 코드 |
| 번호 매기기, 목록 관리 | `lab.py` (ID 발급, 검색, 검증, 요약본) | 파이썬 도구 |
| 연구실 사서 | 기록 담당 + `/ai-lab:archive` | subagent + skill |
| 자율 실험 반복 | 자율 탐색 캠페인 `/ai-lab:campaign` + 강태오(자율 탐색) | skill + subagent + `lab.py`의 판정 엔진 + `/goal` |
| 결과 검증 담당 조교 | `lab.py audit`, `lab.py verify` (숫자·계획·보고서 대조) | 파이썬 도구 |
| 학기 계획과 회고 | 주기(`state/cycle.md`), 로드맵(`ROADMAP.md`) | 파일 + 회의 유형 |

### 한 가지 솔직하게 알려 드릴 것

랩미팅에서 윤하진, 서도윤, 민채원 등이 번갈아 말하지만, **회의 중의 발언은 사실 메인 Claude 한 명이 각 연구원의 관점을 맡아 연기하는 것**이에요. 회의 때마다 여러 AI를 따로 부르면 사용량이 몇 배로 늘기 때문에 이렇게 설계했어요. 관점이 서로 다르게 정해져 있어서(`team.md`) 실제로 반대 의견도 나옵니다.

반면 **실무**(문헌 조사, 실험, 비평, 보고서, 기록)와 **브레인스토밍**은 실제로 **별도의 AI(subagent)** 가 따로 일해요. 특히 브레인스토밍은 서로의 답을 보지 않고 동시에 아이디어를 내서, 생각이 한쪽으로 쏠리지 않게 합니다.

## 4. 명령 한 번에 뒤에서 일어나는 일

`/ai-lab:work`를 입력했을 때를 예로 들어 볼게요.

```
교수님: /ai-lab:work
   │
   ▼
① 메인 Claude가 work 절차서(skill)를 읽는다
   │
   ▼
② lab.py로 남은 할 일을 확인한다 → A-003 "grokking 선행연구 조사" (담당: 문헌)
   │
   ▼
③ 과업 지시서를 쓴다 → briefs/TASK-004.md
   (목표, 목적의 사슬, 필요한 사실만, 산출물 경로, 예산, 하지 말 것)
   │
   ▼
④ 민채원(scout subagent)을 부른다: "briefs/TASK-004.md를 읽고 LIT-002를 만들어"
   │        ┌───────────────────────────────────────────┐
   │        │ 민채원의 별도 컨텍스트                       │
   │        │  - 지시서를 읽는다                           │
   │        │  - lab.py로 이미 읽은 논문이 있는지 확인한다   │
   │        │  - 웹에서 논문을 찾아 실제로 열어 본다         │
   │        │  - 논문마다 P- 항목을 만들고 LIT-002를 쓴다    │
   │        │  - 10줄 이하로 보고한다                      │
   │        └───────────────────────────────────────────┘
   ▼
⑤ 메인 Claude가 보고를 받아 할 일을 완료 처리하고, 회의록의 작업 로그에 한 줄 남긴다
   │
   ▼
⑥ 다음 할 일로 → … → 교수님 결정이 필요하면 멈추고 여쭤본다
   │
   ▼
⑦ 인계 메모를 새로 쓰고, 교수님께 결과 표와 다음 명령을 알려 드린다
```

핵심은 이거예요.
- **긴 일은 subagent가 자기 책상에서** 하고, 메인에는 **짧은 보고만** 돌아와요.
- 모든 결과는 **파일**로 남아서, 다음 세션에서도 이어집니다.
- **교수님 결정이 필요한 순간**에는 반드시 멈춰요.

## 5. AI 연구원들과 일하는 요령

### 말하는 법

- **구체적으로 말해 주세요.** "실험 좀 돌려봐"보다 "EXP-003을 시드 3개로, 학습률 두 가지만 비교해 줘"가 훨씬 정확해요.
- **결정은 분명하게.** 여쭤보면 "A로 하자", "승인", "보류, 이유는 ~"처럼 답하시면 기록도 깔끔하게 남아요.
- **의심 가면 근거를 물어보세요.** "그 숫자 어디서 나왔어?", "근거 파일 보여줘". 모든 숫자는 파일에서 나오도록 되어 있어서 바로 확인할 수 있어요.
- **틀렸으면 바로 말해 주세요.** "그건 내 의도가 아니야, ~라는 뜻이었어". 규칙으로 남기고 싶으면 "앞으로도 이렇게 해줘"라고 덧붙이세요.
- **한 번에 한 가지씩.** 여러 주제를 섞으면 대화가 길어지고 헷갈려요. 주제가 바뀌면 `/clear` 후 새로 시작해도 괜찮아요 (기록은 파일에 남아 있어요).

### AI가 잘하는 것과 조심해야 할 것

| 잘하는 것 | 조심해야 할 것 |
|---|---|
| 코드 작성, 디버깅, 반복 작업 | 그럴듯하지만 틀린 말을 할 수 있어요 (환각) |
| 문헌을 빠르게 훑고 정리하기 | 없는 논문이나 숫자를 지어낼 위험 |
| 여러 관점에서 아이디어 내기 | 결과가 좋아 보이면 과하게 해석하는 경향 |
| 규칙대로 꼼꼼하게 기록하기 | 애매한 지시를 멋대로 해석할 수 있음 |
| 수십 번 반복해서 시도하기 | **스스로 평가하면 개선이 없어도 "좋아졌다"고 착각함** (연구에서 반복 중 절반 이상이 실제로는 변화가 없었음) |
| 코드와 문서를 빠르게 쓰기 | 끝내야 한다는 압박을 받으면 없는 데이터를 지어내기도 함 |

이 연구실은 오른쪽 위험을 막으려고 여러 장치를 넣어 두었어요. 가장 중요한 원칙은 **"제안은 AI가, 판정은 코드가"** 예요.
- 결과가 좋아졌는지는 AI가 말하는 게 아니라 **코드가 지표로 판정**해요. 자율 탐색 캠페인에서도 평가 코드는 잠겨 있고, 채택/기각은 `lab.py`가 정해요.
- 모든 연구원에게 "실패를 그대로 보고하는 것도 성공"이라고 알려 두었어요. 끝내야 한다는 압박을 없애야 날조가 줄어든다는 연구 결과가 있어요.
- 논문은 **실제로 조회해 본 것만** 인용하고, `lab.py lit check`로 실존 여부를 확인해요.
- 숫자는 **코드가 만든 파일**에서만 가져오고, `lab.py audit`이 실행 기록, 계획, 보고서의 숫자를 모두 대조해요.
- 본 실험 전에 **예측과 중단 기준을 미리 적어요** (사전 등록).
- 오세린(비평가)이 **코드와 로그까지** 확인해요.
- 결과 확정, 방향 전환, 본 실험 착수는 **교수님만** 결정해요.
- 애매하면 **여쭤보도록** 규칙이 되어 있어요.

그래도 **최종 판단은 교수님 몫**이에요. 중요한 결과는 보고서와 근거 파일을 직접 한 번 보시길 권해요.

### 허락 창이 뜨면

- 창에 **무엇을 하려는지**(어떤 명령, 어떤 파일)가 보여요. 읽어 보고 이해되면 승인, 이상하면 거절하세요.
- 거절해도 괜찮아요. Claude는 다른 방법을 찾거나 이유를 물어봐요.
- 파일을 지우거나 외부로 뭔가를 보내는 명령은 특히 주의 깊게 보세요.

## 6. 안전과 비용

### 어떤 데이터가 어디로 가나요

- Claude가 **읽는 모든 내용**(파일, 명령 결과, 대화)은 Anthropic의 서버로 전송돼서 처리돼요.
- 그래서 **회사 데이터, 사내 코드와 문서, 개인정보, 비밀번호, API 키는 연구실에 넣지 마세요.** (연구실 규칙에도 들어 있어요.)
- 회사 문제는 기밀이 아닌 일반화된 형태로 설명하고, 결과물은 릴리스로 가져가요 ([사용설명서 14장](사용설명서.md#14-회사로-결과물-가져가기)).

### 공개 저장소 주의

- 환경 저장소 [yhlee52/ai_sci_cowork](https://github.com/yhlee52/ai_sci_cowork)는 **공개(public)** 예요. 누구나 볼 수 있어요.
  - 환경에는 비밀 정보가 없어서 공개해도 괜찮아요. 다만 앞으로 고칠 때도 개인 정보나 키를 넣지 않도록 주의하세요.
- **연구실 저장소는 비공개(private)로** 만드는 것을 강하게 권해요. 아직 발표하지 않은 아이디어와 결과가 들어 있으니까요 (7-5절).

### 사용량 확인

| 쓰는 방식 | 확인 방법 |
|---|---|
| 구독 (Pro, Max) | `/status` — 남은 사용량. 5시간마다, 그리고 주 단위로 한도가 있어요 |
| API 키 (사용한 만큼 결제) | `/cost` — 이번 세션에서 쓴 토큰과 금액 |

사용량을 아끼는 가장 쉬운 방법:
- 일상 운영은 `/model sonnet`으로 해요.
- 단계가 바뀔 때 `/clear`로 대화를 비워요 (기록은 파일에 남아 있어요).
- 연구실 설정의 예산 프로필은 `economy`(기본)를 써요.

## 7. GitHub으로 관리하기

### 7-1. 저장소가 두 종류예요

| 저장소 | 무엇이 들어 있나 | 공개 여부 | 예 |
|---|---|---|---|
| **환경 저장소** | 연구실을 만드는 틀: agent, skill, hook, 도구, 템플릿, 문서 | 공개 (지금 설정) | `yhlee52/ai_sci_cowork` |
| **연구실 저장소** | 실제 연구 결과물: 회의록, 실험, 지식베이스 | **비공개 권장** | `yhlee52/grokking-lab` (연구실마다 하나) |

환경은 한 번 잘 만들어 두고 계속 고쳐 쓰고, 연구실은 주제마다 새로 만드는 구조예요.

### 7-2. git 기초 용어 (딱 이 정도만)

| 용어 | 뜻 | 비유 |
|---|---|---|
| 저장소 (repository) | 파일과 그 변경 이력을 담는 폴더 | 이력이 남는 공유 폴더 |
| 커밋 (commit) | 지금까지의 변경을 하나의 기록으로 저장 | "여기까지 저장" 버튼 + 메모 |
| 푸시 (push) | 내 PC의 커밋을 GitHub에 올리기 | 업로드 |
| 풀 (pull) | GitHub의 새 커밋을 내 PC로 받기 | 다운로드 |
| 클론 (clone) | GitHub 저장소를 내 PC에 통째로 복사 | 처음 한 번 내려받기 |

> 명령을 외울 필요는 없어요. Claude Code에게 **"지금 변경사항 커밋하고 푸시해줘"**, **"GitHub에서 최신 버전 받아줘"** 라고 말하면 대신 해 줘요. 아래 명령은 무슨 일이 일어나는지 이해하기 위한 참고용이에요.

### 7-3. 다른 PC에서 쓰기 (가장 흔한 경우)

환경을 고치지 않고 **쓰기만** 한다면, 어느 PC에서든 Claude Code에 이 두 줄이면 끝이에요.

```
/plugin marketplace add yhlee52/ai_sci_cowork
/plugin install ai-lab@ai-sci-cowork
```

환경 저장소가 업데이트되면:

```
/plugin marketplace update ai-sci-cowork
```

그다음 Claude Code를 다시 시작하세요.

> **VSCode 확장을 쓴다면:** 확장 채팅창은 `/plugin` 명령을 지원하지 않아요(`isn't available in this environment`). 이 장의 `/plugin ...` 명령은 모두 VSCode 터미널에서 `claude plugin ...`으로 바꿔 실행하세요 (예: `claude plugin marketplace update ai-sci-cowork`). 업데이트할 때는 `claude plugin update ai-lab@ai-sci-cowork`도 함께 실행하세요. `claude`가 없다고 나올 때의 방법은 [사용설명서 3장](사용설명서.md#3-설치하기)에 있어요.

### 7-4. 환경을 고치고 GitHub에 올리는 흐름

환경(agent 규칙, 명령 절차, 템플릿 등)을 바꾸고 싶을 때의 순서예요.

**① 내 PC에 환경 저장소 준비 (처음 한 번)**

지금 이 폴더가 이미 환경 저장소예요. 다른 PC라면 먼저 내려받아요.

```
git clone https://github.com/yhlee52/ai_sci_cowork.git
```

**② 고치기**

- 직접 고쳐도 되고, 이 폴더에서 Claude Code를 열고 **"비평가가 리뷰할 때 ~도 확인하게 바꿔줘"** 처럼 부탁해도 돼요.
- 어느 파일을 고치면 되는지는 [사용설명서 17장](사용설명서.md#17-환경-자체를-고치고-싶을-때)에 표로 정리되어 있어요.

**③ 버전 올리기**

`.claude-plugin/plugin.json`의 `"version"` 숫자를 올려요 (예: `0.5.0` → `0.5.1`). 이걸 올려야 설치된 곳에서 "새 버전"으로 알아봐요.

**④ 커밋하고 푸시하기**

```
git add .
git commit -m "비평가가 데이터 누수를 더 꼼꼼히 확인하도록 수정"
git push
```

또는 Claude에게: "변경사항 커밋하고 푸시해줘. 메시지는 한글로."

**⑤ 쓰는 PC에서 업데이트 받기**

```
/plugin marketplace update ai-sci-cowork
```

그다음 Claude Code를 다시 시작해요.

> **알아 두세요:** `templates/workspace/`(새 연구실의 기본 파일)를 고쳐도 **이미 만든 연구실에는 적용되지 않아요.** 기존 연구실에도 반영하고 싶으면 그 연구실 폴더에서 Claude에게 "환경 템플릿의 ~ 변경을 이 연구실에도 반영해줘"라고 부탁하세요.

#### 고치면서 바로 시험해 보고 싶다면

GitHub에 올리기 전에 이 PC에서 먼저 시험하려면, GitHub 대신 **내 PC의 폴더**를 marketplace로 등록하면 돼요. 같은 이름이라 먼저 지우고 등록해요.

```
/plugin marketplace remove ai-sci-cowork
/plugin marketplace add "<환경 저장소를 내려받은 폴더 경로>"
/plugin install ai-lab@ai-sci-cowork
```

이렇게 하면 폴더를 고친 뒤 `/plugin marketplace update ai-sci-cowork`만으로 바로 반영돼요. 시험이 끝나면 다시 GitHub 주소로 바꿔 등록해도 되고, 이 PC에서는 계속 폴더 방식으로 써도 괜찮아요.

### 7-5. 연구실을 GitHub에 올리기 (비공개로)

`/ai-lab:new-lab`으로 만든 연구실 폴더는 이미 git 저장소예요. GitHub에 **비공개**로 올리려면 연구실 폴더에서 Claude에게 이렇게 말하세요.

> "이 연구실을 GitHub에 비공개 저장소로 만들어서 올려줘. 이름은 grokking-lab."

Claude는 대략 이런 명령을 실행해요 (GitHub CLI `gh`가 설치되어 있고 로그인되어 있어야 해요).

```
git add .
git commit -m "연구실 설립"
gh repo create grokking-lab --private --source . --push
```

그다음부터는 세션을 마칠 때마다 "커밋하고 푸시해줘" 한 마디면 돼요.

- 실험의 큰 파일(체크포인트, 데이터셋, `runs/` 폴더)은 `.gitignore`에 의해 자동으로 빠져요.
- 회사로 가져갈 릴리스(md 문서)는 연구실 기록의 일부라서 함께 올라가요. 연구실 저장소를 비공개로 두어야 하는 또 하나의 이유예요.

### 7-6. 라이선스에 대해

공개 저장소에 라이선스 파일이 없으면, 다른 사람은 코드를 볼 수는 있어도 법적으로 가져다 쓸 수는 없어요. 다른 사람도 쓰게 하고 싶다면 `LICENSE` 파일을 추가하세요 (예: MIT). 원하시면 Claude에게 "MIT 라이선스 추가해줘"라고 하면 돼요. 혼자만 쓸 거라면 없어도 괜찮아요.

## 8. 자주 하는 질문 (개념 편)

**Q. AI 연구원들이 서로 진짜로 대화하나요?**
랩미팅은 메인 Claude 한 명이 여러 연구원의 관점을 맡아 진행해요 (3장). 실무와 브레인스토밍은 실제로 별도의 AI가 따로 일하고, 서로는 **파일**을 통해 결과를 주고받아요. 사람 연구실에서 보고서로 일을 넘기는 것과 비슷해요.

**Q. 연구원들이 저를 기억하나요?**
대화 자체는 기억하지 못해요. 대신 회의록, 결정 기록, 인계 메모, 지식베이스, 연구원별 수첩(memory)이 파일로 남아서, 세션이 시작될 때마다 필요한 만큼 읽고 이어 가요. 교수님이 선호하는 방식도 "앞으로도 이렇게 해줘"라고 말하면 규칙이나 기억으로 남길 수 있어요.

**Q. 자율 탐색을 맡겨 두면 AI가 멋대로 연구 방향을 바꾸지 않나요?**
자율 탐색 캠페인은 낮이든 밤이든 교수님이 승인한 계약(바꿔도 되는 파일, 예산, 멈춤 조건) 안에서만 움직여요. 계약 밖의 일이 필요해지면 멈추고 결정 대기함에 질문을 남겨요. 그리고 캠페인의 결과도 교수님이 확정하기 전까지는 "잠정"이에요.

**Q. 결과를 믿어도 되나요?**
여러 겹의 확인 장치가 있지만(5장), AI는 틀릴 수 있어요. 결과 확정은 교수님이 하도록 되어 있으니, 중요한 결과는 보고서와 `lab.py verify` 결과, 오세린의 리뷰를 직접 보고 판단하세요.

**Q. 회의 중에 제가 틀린 말을 하면요?**
연구원들은 교수님을 존중하지만, 근거가 있으면 반대 의견을 내도록 되어 있어요. 반대 의견은 회의록에 남고, 최종 결정은 교수님이 해요.

**Q. 연구원을 더 늘리거나 성격을 바꿀 수 있나요?**
성격과 관점은 연구실의 `team.md`에서 바로 바꿀 수 있어요. 새 실무 연구원(subagent)을 추가하려면 환경 저장소의 `agents/`에 파일을 추가해야 해요. Claude에게 "통계 전담 연구원을 한 명 추가해줘"라고 부탁하면 초안을 만들어 줘요.

**Q. 인터넷이 끊기면요?**
Claude는 인터넷으로 동작해서, 끊기면 멈춰요. 다시 연결되면 새 세션에서 인계 메모부터 이어 가면 돼요. 이미 실행 중이던 실험 파일과 기록은 그대로 남아 있어요.

**Q. 연구실을 여러 개 동시에 운영할 수 있나요?**
네. 연구실마다 폴더(와 저장소)가 따로라서 기록이 섞이지 않아요. 환경(plugin)은 하나를 같이 써요.

**Q. 뭔가 이상하게 돌아가면 어떻게 하나요?**
먼저 Claude에게 "지금 뭐 하고 있어? 왜 그렇게 했어?"라고 물어보세요. 멈추게 하고 싶으면 Esc를 누르면 돼요. 파일이 이상하게 바뀌었으면 git으로 이전 상태를 확인할 수 있어요 ("마지막 커밋 이후 뭐가 바뀌었는지 보여줘").
