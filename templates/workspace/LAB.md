## 구성

교수님(지도교수, 최종 결정)과 AI 연구원들, 기록 담당으로 구성된다. 역할과 관점은 `team.md`에 있다.

## 연구 원칙

1. **방향은 사람이, 숫자는 코드가 정한다.** AI 연구원은 제안하고, 결과가 좋아졌는지는 코드(`labkit`, `lab.py audit`, 캠페인 판정)가 판정한다. AI가 스스로 "개선됐다"고 판단한 것은 증거가 아니다.
2. **모든 주장은 추적 가능해야 한다.** 주장 → 결과(F-) → 결과 파일 → 실행 기록, 인용 → 실존 확인된 논문 항목(P-).
3. **정직한 실패도 성공이다.** 끝내야 한다는 압박은 없다. 실행이 실패하거나 데이터가 없으면 그대로 보고한다. 가짜 데이터나 임시 값으로 채우지 않는다.
4. **효과 없음도 지식이다.** 영(null)·부정적 결과는 결과(F-)로 기록한다. 그래야 같은 막다른 길을 다시 걷지 않는다.
5. 작고 빠르게 검증한다. 본 실험 전에 반드시 파일럿으로 신호를 확인한다.
6. 본 실험 전에 예측, 성공 기준, 중단 기준을 먼저 적는다 (사전 등록). 결과를 본 뒤 가설을 바꾸지 않는다.
7. 검증한 범위 밖으로 주장하지 않는다. 메커니즘을 주장하려면 조건을 바꿔도 예측대로 움직이는지 확인한다 (조건 이동 점검).
8. 계산 예산을 존중한다. 한 번의 실행은 `lab.config.json`의 `max_run_minutes`를 넘기지 않고, `lab.py`가 이 PC를 탐색해 자동으로 건 하드웨어 제약(`compute.limits`: VRAM 예산, 정밀도, 모델 크기, 동시 실행 수) 안에서 계획한다. 제약을 바꾸는 것은 교수님이 `compute.overrides`로 한다.

## 운영 장소와 데이터 규칙

- 이 연구실은 **회사 밖에서만** 운영한다. 회사 안에서는 릴리스(`research/releases/REL-*`)만 가져다 쓴다.
- 연구실에서 읽는 모든 내용은 Claude API로 전송된다. 그래서 **회사 데이터, 사내 코드, 사내 수치, 사내 문서, 고객 정보는 연구실에 절대 넣지 않는다.** 공개 데이터와 공개 논문, 직접 만든 합성 데이터만 쓴다.
- 회사 문제를 다루고 싶으면, 기밀이 아닌 일반화된 형태로 바꿔 교수님이 직접 설명한다 (예: "시계열 이상 탐지, 샘플 1만 개 규모").
- 회사 안으로는 md 파일만 가져갈 수 있다. 회사로 가져갈 결과물은 `/ai-lab:release`로 md 문서(본문 + 선택적 코드 묶음)로 만든다. 무엇을 넣을지는 교수님이 정한다 (C 등급). 데이터셋, 모델, 코드의 **회사 사용 가능 라이선스**를 확인한다.

## 의사결정 규칙

연구가 엉뚱한 방향으로 흘러가지 않도록, 결정의 무게에 따라 누가 정하는지를 나눈다.

| 등급 | 무엇 | 누가 정하나 | 방법 |
|---|---|---|---|
| **A. 자율** | 구현 방식, 승인된 계획 안의 하이퍼파라미터, 디버깅, **파일럿 실행**, 문헌 검색, **승인된 캠페인 안의 시도** | 담당 연구원 | 바로 하고 작업 로그에 남긴다 |
| **B. 동료 협의** | 승인된 계획 안에서의 설계 변경, 애매한 결과의 해석, 파일럿 결과에 따른 조정 | 담당 연구원 + 다른 연구원 1명 이상 (주로 오세린) | 리뷰(REV) 또는 회의에서 의견을 받고 기록한다 |
| **C. 교수님 결정** | 새 연구 방향, 본 실험 착수(사전 등록 승인), **캠페인 계약 승인**, 가설 폐기, 결과 확정(accepted), 예산 초과, 로드맵과 주기 목표 변경, 결과가 기존 지식과 모순될 때, 지시가 애매할 때 | **교수님** | 대화로 직접 여쭙는다. 교수님이 자리에 없으면 결정 대기함(`state/inbox.json`)에 올리고 **기다린다** |

- 판단이 애매하면 한 단계 위의 등급으로 취급한다.
- C 등급을 기다리는 동안에는 그 결정에 의존하지 않는 다른 일만 진행한다.
- 모든 B, C 결정은 회의록과 `kb/decisions/`에 이유와 이견과 함께 남는다.

## 연구 생애주기

```
아이디어 → 재현·공정한 기준선 → 파일럿 → 제안(사전 등록) → 본 실험 또는 캠페인 → 감사·리뷰 → (조건 이동 점검) → 결과 확정 → 보고
  [회의]         [A]              [A]      [C: 승인 = 착수]          [A]              [B]            [A]          [C: 확정]
```
- **재현·공정한 기준선**: 기준선이 알려진 수치를 대략 재현하고, 새 방법과 같은 예산으로 조정되어야 비교가 공정하다.
- **파일럿**은 2분 이내, 1 시드의 작은 실행이다. 코드가 도는지, 신호가 있는지만 본다. 파일럿 수치는 증거가 아니다.
- **제안서**는 `plan.md`의 사전 등록(예측, 성공 기준, 중단 기준)이다. 교수님이 승인하면 plan.md 상태가 `approved`가 되고, 그때부터 본 실험을 돌린다.
- **캠페인**은 지표 하나를 놓고 여러 변형을 자율로 시도하는 탐색이다. 교수님이 시키면 언제든 시작한다 (지금 바로, 또는 자리를 비운 사이나 밤새). 교수님이 계약(범위, 예산, 멈춤 조건)을 승인하면, 그 안에서는 연구원이 시도하고 `lab.py`가 지표로 채택·기각을 판정한다. 끝나면 탐색에 쓰지 않은 새 시드로 확인 실험을 한다.
- **감사**(`lab.py audit`): 결과 숫자가 실행 기록과 같은지, 계획대로 실행했는지, 보고서의 숫자가 결과 파일에 있는지 코드가 확인한다.
- **조건 이동 점검**: "왜 좋아졌는지(메커니즘)"를 주장하려면, 조건을 하나 바꿨을 때 그 메커니즘이 예측하는 대로 결과가 움직이는지 확인한다. 하지 않았으면 주장을 검증한 조건으로 한정한다.

## 운영 리듬

- 세션마다 번호를 붙인다 (session 001, 002, …). 세션 N개가 한 **주기(cycle)** 다 (`lab.config.json` → `cycle_sessions`).
- 주기 시작: 계획 회의 → 주기 동안: 진행 점검, 브레인스토밍, 작업, 결과 리뷰 → 주기 끝: 회고.
- 세션 끝: 지식베이스 정리(archive)와 인계 메모.
- 교수님은 언제든 회의에 끼어들어 의견을 내거나 방향을 바꿀 수 있다. 교수님과 연구원 한 명의 1:1도 가능하다.
